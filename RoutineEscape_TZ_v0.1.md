# RoutineEscape — техническое задание

**Версия ТЗ:** 0.2 (16 сентября 2026; имя файла сохранено)
**Статус:** MVP planning — автоматические локальные правила, без AI
**Платформа:** Telegram Bot  
**Основной стек:** C# / .NET  
**Название проекта:** RoutineEscape

---

## 1. Идея проекта

RoutineEscape — Telegram-бот для задач, событий, напоминаний и заметок из обычных и пересланных сообщений.

> Пользователь отправляет сообщение; программа распознаёт тип по локальным правилам, показывает Draft и сохраняет его после подтверждения. При неоднозначности пользователь уточняет тип.

Решение от 16 сентября 2026: AI/LLM исключён из требований и дальнейшего плана. Автоматическое распознавание детерминированными правилами — основной сценарий; ручной выбор нужен, если правило не сработало или результат неверен. Даты и время также разбираются без LLM.

Пример: «созвон завтра в 19:00» → предложение события с датой и временем → «✅ Добавить». Вариант «созвон завтра в девятнадцать ноль ноль» нормализуется в тот же результат.

## 3. Основной UX-принцип

### 3.1. Создание сущностей без обязательных команд

Пользователь пишет или пересылает текст. При уверенном совпадении с правилом бот сразу предлагает задачу, событие, напоминание или заметку. Обязательный предварительный выбор типа не нужен.

Бот сохраняет текст и источник, локально выделяет дату/время и показывает Draft. Пользователь подтверждает результат либо уточняет тип и поля. При отсутствии подходящего правила или конфликте признаков бот предлагает четыре типа вручную.

### 3.2. Команды используются только для навигации

- `/start`
- `/list`
- `/timezone`
- `/today`
- `/tasks`
- `/events`
- `/notes`
- `/settings`
- `/help`

Команды не обязательны для создания новых сущностей.

## 5. Обработка входящего сообщения

```text

      ↓

      ↓
Локальные правила классификации и извлечения даты
      ↓
Draft: предложение типа / ручное уточнение
      ↓

      ↓

      ↓
Persistence
      ↓

```

## 6. Автоматическое определение типа по правилам

Признаки типов:

- явное «напомни» / «напоминание» → Reminder;
- «созвон», «встреча», «собеседование» и подобные признаки → Event;
- «купить», «отправить», «оплатить» и другие действия → Task;
- действие с «через N минут/часов» → Reminder;
- «заметка», «номер аудитории», «адрес», «рецепт», ссылка → Note.

Конфликтующие признаки, отрицание и отсутствие известного правила → Unknown и ручной выбор. Не требуется универсальное понимание произвольного русского текста.

При уверенном правиле бот показывает предполагаемый тип, исходный текст и извлечённые выражения даты/времени, кнопку добавления, альтернативные типы и отмену. Значение confidence в существующей модели обозначает результат правила, а не вероятность LLM.

Сущность сохраняется только после действия пользователя. Для Event и Reminder нужны определённые дата и время (либо относительный интервал). При отсутствии, неверном или неоднозначном значении бот просит уточнение и ничего не сохраняет. Сейчас уточнение выполняется повторной отправкой исправленного сообщения.

Task может быть без deadline, Note не требует даты. Редактирование полей существующего Draft остаётся планируемой частью соответствующих flow.

## 7. Пересланные сообщения

Пересылка сообщений — одна из главных функций RoutineEscape.

Пользователь должен иметь возможность просто переслать любое доступное для пересылки Telegram-сообщение в чат с ботом.

Бот должен:

1. определить, что сообщение переслано;
2. сохранить содержимое;
3. извлечь данные об источнике;
4. определить тип локальными правилами или запросить ручное уточнение;
5. показать источник в Draft;
6. сохранить информацию об источнике вместе с сущностью.

## 8. Источник пересланного сообщения

Telegram Bot API предоставляет информацию о происхождении пересланного сообщения через `forward_origin`.

Нужно поддерживать четыре варианта источника.

### 8.1. Известный пользователь

Тип:

```text
MessageOriginUser
```

Сохранять при наличии:

- Telegram User ID;
- FirstName;
- LastName;
- Username;
- DisplayName;
- OriginalMessageDate.

Отображение:

```text
Источник: Иван Иванов (@ivan)
```

Если username отсутствует:

```text
Источник: Иван Иванов
```

---

### 8.2. Пользователь со скрытыми данными

Тип:

```text
MessageOriginHiddenUser
```

Telegram не передаёт объект пользователя, но передаёт строку с именем отправителя.

Сохранять:

- SenderDisplayName;
- OriginalMessageDate;
- IsHiddenUser = true.

Пример:

```text
Источник: Иван Иванов
```

В этом случае:

- нельзя предполагать Telegram ID;
- нельзя придумывать username;
- нельзя пытаться связать это имя с другим пользователем;
- имя хранится только как отображаемая строка из Telegram.

---

### 8.3. Чат / группа

Тип:

```text

```

Сохранять:

- ChatId;
- ChatTitle;
- ChatUsername — если доступен;
- AuthorSignature — если доступна;
- OriginalMessageDate.

Отображение:

```text

```

При наличии подписи:

```text

```

### 8.4. Канал

Тип:


Сохранять:

- ChannelId;

## 11. Извлечение данных без LLM

Тип предлагает локальное правило либо выбирает пользователь при неоднозначности. Исходный текст используется как начальное название/содержимое, без обязательной смысловой переформулировки. Название, описание, место и приоритет пользователь может изменить вручную.

Локальный парсер выделяет из исходного текста поддерживаемые выражения даты, времени и интервала, затем передаёт их Date/Time Resolver. Этот путь должен работать при отсутствии AI-ключей и без сетевого обращения к LLM.

Пример: из «Скинь Диме документы до среды вечером» для выбранной задачи можно выделить «до среды» и «вечером»; название остаётся исходным текстом до ручного редактирования. Извлечение человека, места и других смысловых сущностей не требуется. Повторяемость относится к этапу после MVP.

## 15. Уведомления

Согласованный сценарий: первая доставка в заданное время для активного Reminder, незавершённой Task с явно указанным временем и Event. Один повтор через 10 минут после успешной первой доставки, если пользователь не подтвердил и не отложил. Бесконечных повторов нет.

Кнопки: «Готово», «Отложить на 10 минут», «На час». «Готово» завершает задачу/напоминание и отменяет будущие доставки. Для события подтверждает только уведомление. Перенос считается от нажатия и запускает новый цикл с одним повтором; прежние кнопки становятся недействительными. У события откладывается уведомление, не само событие.

Дата задачи без явно указанного времени не означает уведомление в полночь. Бот сообщает, что нужно назначить время. Часовой пояс проверяется/меняется через /timezone; существующие UTC-моменты не переносятся молча.

Расписания, этап доставки и retries хранятся в PostgreSQL. Изменение времени, завершение и удаление записи синхронизируют очередь. При первом включении историческая просрочка не рассылается; старые задачи требуют повторного задания точного времени, будущие Reminder/Event включаются миграцией. После обычного перезапуска просрочка до 24 часов доставляется, более старая приостанавливается.

Фоновая проверка — каждые 5 секунд. Ошибки отправки повторяются с увеличением задержки до 15 минут, максимум 8 попыток, затем приостановка до нового срока. PostgreSQL-блокировки предотвращают конкурентную обработку одной доставки. При сетевой неопределённости возможен дубль: exactly-once не гарантируется. Тестовые сообщения не отправляются в реальные чаты.

## 19. AI / LLM — исключено из плана

AI/LLM не требуется ни для MVP, ни как запланированное расширение. Не нужны классификация через LLM, генерация названия, structured output провайдера и настройка AI-ключей. Автоматическое определение типа выполняется локальными правилами.

Уже существующие RoutineEscape.AI и связанные интерфейсы/тесты сохраняются как необязательный код прежней реализации вне актуального плана. LLM-адаптер не подключён к штатному pipeline. Его демонтаж не входит в текущую задачу.

## 20. Локальный разбор даты и времени

Разбор по правилам — основной путь, а не запасной режим. Он включает выделение выражений из исходного сообщения и преобразование их в дату/время с учётом TimeZone (раздел 12).

Неизвестные или неоднозначные выражения требуют уточнения. Для остального текста достаточно ручного ввода полей; универсальный семантический интерпретатор не нужен.

RuleBasedMessageInterpreter выделяет выражения из текста без LLM; RussianDateTimeResolver преобразует их при подтверждении Draft. Неизвестные даты и неоднозначное локальное время отклоняются. Относительные интервалы отсчитываются от создания Draft, а не нажатия подтверждения.

### Компактный обзор после сохранения

После сохранения любого из четырёх типов бот отправляет подтверждение с названием и датой новой записи и сводку максимум из пяти других записей текущего пользователя. Окно дат — сегодня и следующие два календарных дня в TimeZone пользователя; дополнительно показываются самые свежие заметки и задачи без срока (до двух зарезервированных мест, остальные свободные места тоже заполняются). Датированные пункты сортируются по времени, без даты — по убыванию даты создания. Новая запись не дублируется, длинные названия сокращаются, пустых секций нет.

«Показать всё» открывает актуальный список текущего пользователя по пять пунктов с пагинацией и счётчиком страниц. Только незавершённые задачи и активные напоминания; прошлые завершившиеся события исключаются, заметки доступны все. Просроченные активные пункты доступны в полном списке. Отдельно указывается количество дополнительных записей. Автор callback определяет владельца списка; ответ отправляется ему в личный чат.

---
### Управление сохранёнными записями

Из сводки и страниц списка пользователь открывает конкретную запись. Карточка содержит текст, дату, часовой пояс, статус и действия. Для задачи доступны выполнение и восстановление. Все четыре типа поддерживают подтверждаемое удаление и редактирование названия/содержимого; задача — срока (включая снятие срока), событие/активное напоминание — даты и времени. Минимальный набор не включает редактирование описания, приоритета, места и тегов.

Редактирование запрашивает одно поле за раз с примерами допустимого ввода; текст не должен создавать отдельный Draft. Неверное значение не меняет исходную запись, пользователь может повторить ввод или отменить кнопкой/командой /cancel. Используется TimeZone пользователя и локальный resolver. После сохранения показывается свежая карточка, после удаления — список. Удаление требует отдельной кнопки «Да, удалить» и предоставляет отмену.

Все callback и состояния привязаны к владельцу. Устаревшие кнопки, повторные нажатия, удалённые записи и изменение записи во время редактирования обрабатываются без порчи данных. Срок режима — 15 минут; состояние локального экземпляра переживает перезапуск. Сохраняются ограничения длины сообщений и пагинация.

# 32. MVP Definition of Done

MVP считается готовым, когда пользователь может:

1. запустить `/start`;
2. отправить обычное сообщение;
3. переслать сообщение от другого человека / чата / канала;
4. увидеть корректно распознанный источник;
5. получить тип по локальным правилам без AI;
6. выбрать тип вручную при неоднозначности и изменить поля Draft до сохранения;
7. подтвердить Draft;
8. создать Task;
9. создать Event;
10. создать Reminder;
11. создать Note;
12. получить напоминание в нужное время;
13. посмотреть свои задачи и события;
14. завершить задачу;
15. удалить сущность;
16. изменить настройки TimeZone;
17. получить дату из поддерживаемого русского выражения без LLM либо уточнить её вручную.

Дополнительно:

- основной сценарий полностью работает без AI-ключей и обращений к LLM;

# 35. Главный продуктовый критерий

Пользователь должен получить предложение по локальным правилам и сохранить его подтверждением, без обязательного предварительного выбора типа, команд и настройки AI. Ручной выбор остаётся для уточнения.

Локальный разбор дат сокращает ввод, но пользователь всегда может исправить результат. Неизвестные значения нужно уточнять, сохраняя исходный текст и источник.

Число без месяца («23го», «23-го», «23 го», «23 числа», с необязательным «числа» после «го») означает текущий месяц пользователя. Невозможная или прошедшая дата требует уточнения месяца, например «23 сентября в 13:00»; автоматического переноса на следующий месяц нет. Исходный текст и классификация не меняются.
